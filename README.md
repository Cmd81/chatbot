# 📹 تماس تصویری ناشناس

یک MVP برای تماس تصویری تصادفی و ناشناس که از دو مسیر در دسترس است:

1. **ربات تلگرام + Telegram Mini App**
2. **یک صفحه‌ی وب معمولی روی همان دامنه**

منطق مچ ساده است: نفر اول وارد می‌شود و منتظر می‌ماند؛ به‌محض ورود نفر دوم،
این دو به هم وصل می‌شوند و تماس تصویری شروع می‌شود. بدون فیلتر، بدون سکه و
بدون دیتابیس.

## ویژگی‌ها

| | |
|---|---|
| 🔒 **ناشناس** | نام، شماره و آی‌دی تلگرام به طرف مقابل نمی‌رسد. هویت کاربر در LiveKit یک رشته‌ی تصادفی (`anon_…`) است. |
| 🛡️ **بدون نشت IP** | کل ویدیو و صدا از SFU (LiveKit) رد می‌شود. هیچ اتصال P2P بین دو کاربر برقرار نمی‌شود و ICE candidateهای طرفین با هم مبادله نمی‌شود. |
| 🌐 **مقاوم به فیلترینگ** | TURN روی هم UDP 3478 و هم TLS 5349. کاربری که UDP ندارد از مسیر TLS وصل می‌شود. |
| 🧭 **مستقل از IP** | هیچ منطقی (احراز هویت، مچ، rate limit) به IP وابسته نیست؛ همه‌ی کاربران می‌توانند پشت یک VPN با آی‌پی یکسان باشند. |
| 🤖 **چت داخل ربات** | مچ شدن و چت کامل داخل خود تلگرام، بدون باز کردن مینی‌اپ؛ با پشتیبانی از همه‌ی انواع پیام. |
| 💬 **گفتگوی متنی** | روی کانال دادهٔ LiveKit؛ فقط در حافظه و با پایان تماس کاملاً پاک می‌شود. |
| ⏭️ **جریان پیوسته** | دکمه‌ی «نفر بعدی» و برگشت خودکار به صف وقتی طرف مقابل می‌رود — بدون خاموش شدن دوربین. |
| 📱 **موبایل‌محور** | رابط فارسی، راست‌چین، تمام‌صفحه، هماهنگ با تم تلگرام. |
| 🎥 **کیفیت تطبیقی** | تا ۱۰۸۰p؛ بر اساس سرعت اینترنت، توان دستگاه و دوربین خودکار بالا و پایین می‌رود. دکمه‌ی انتخاب دستی هم دارد. |
| ⚡️ **بدون دیتابیس** | مچ‌میکر کاملاً در حافظه است. |

## معماری

```
                    ┌──────────────────────────────────────────┐
   کاربر تلگرام ───▶│  Caddy  (HTTPS خودکار، ریورس‌پراکسی)      │
   کاربر مرورگر ───▶│  :80  :443                :5349 (TLS)    │
                    └────┬──────────────┬──────────────┬───────┘
                         │              │              │
             /  و  /ws   │        /rtc* │              │ TURN خام
                         ▼              ▼              ▼
                 ┌───────────────┐   ┌──────────────────────────┐
                 │   Backend     │   │   LiveKit Server (SFU)    │
                 │ Node + TS     │◀──│  :7880 سیگنالینگ          │
                 │ Fastify + ws  │API│  :7881/tcp  :7882/udp     │
                 │ grammY (بات)  │   │  :3478/udp TURN           │
                 │ مچ‌میکر حافظه‌ای│   │  :5350 TURN پشت TLS      │
                 └───────────────┘   └──────────────────────────┘
```

**چرا `network_mode: host`؟** LiveKit به پورت‌های UDP زیادی نیاز دارد و NAT داکر
برای مدیا مناسب نیست. مزیت مهم دیگر: در این حالت داکر قوانین `ufw` را دور نمی‌زند،
بنابراین فایروال واقعاً اعمال می‌شود. بک‌اند فقط روی `127.0.0.1:3000` گوش می‌دهد و
از بیرون فقط از طریق Caddy در دسترس است.

**چرا `layer4` در Caddy؟** برای اینکه TURN هم بتواند از گواهی Let's Encrypt استفاده
کند، Caddy روی پورت عمومی **5349** دست‌دادن TLS را انجام می‌دهد و ترافیک TURN خام را
به پورت داخلی **5350** در LiveKit می‌فرستد (`turn.external_tls: true`). تمدید گواهی
هم به‌صورت خودکار توسط Caddy انجام می‌شود.

## پیش‌نیازها

- یک سرور اوبونتو/دبیان با دسترسی `root` و آی‌پی عمومی
- دو رکورد **A** در DNS که هر دو به آی‌پی همان سرور اشاره کنند:

  | نام | نوع | مقدار |
  |---|---|---|
  | `chat.example.com` | A | `<آی‌پی سرور>` |
  | `turn.example.com` | A | `<آی‌پی سرور>` |

  > ⚠️ اگر از Cloudflare استفاده می‌کنید، هر دو رکورد باید **DNS only** (ابر خاکستری)
  > باشند. پروکسی Cloudflare نه TURN را پاس می‌دهد و نه صدور گواهی را.

- یک توکن ربات از [@BotFather](https://t.me/BotFather)

## نصب سریع

دو راه وجود دارد:

- **الف) دستی روی سرور** (پایین) — سریع‌ترین راه برای بار اول
- **ب) خودکار با GitHub Actions** — راهنما: [`docs/DEPLOY-GITHUB-ACTIONS.md`](docs/DEPLOY-GITHUB-ACTIONS.md)

```bash
git clone <آدرس-ریپو> anon-video
cd anon-video
./deploy.sh
```

اسکریپت به‌ترتیب این کارها را می‌کند:

1. اگر داکر نصب نباشد، نصبش می‌کند
2. فایل `.env` را می‌سازد و **کلیدهای LiveKit را تصادفی تولید می‌کند**
   (توکن ربات به‌صورت مخفی پرسیده می‌شود و فقط در `.env` با دسترسی `600` ذخیره می‌شود)
3. `ufw` را تنظیم و فعال می‌کند
4. رکوردهای DNS را بررسی می‌کند
5. ایمیج‌ها را می‌سازد و سرویس‌ها را با `restart: unless-stopped` بالا می‌آورد
6. سلامت سرویس‌ها را چک می‌کند

اجرای غیرتعاملی:

```bash
TELEGRAM_BOT_TOKEN=... \
PUBLIC_HOST=chat.example.com \
TURN_HOST=turn.example.com \
ACME_EMAIL=me@example.com \
./deploy.sh
```

بعد از اتمام، بررسی کامل:

```bash
./scripts/verify.sh
```

> 💡 **توکن ربات هرگز داخل گیت نمی‌رود.** فقط در `.env` روی سرور است و `.env` در
> `.gitignore` قرار دارد.

## تنظیم ربات تلگرام

بک‌اند هنگام بالا آمدن این کارها را **خودکار** انجام می‌دهد:

- پاسخ به `/start` با یک پیام فارسی و دکمه‌ی `web_app`
- تنظیم **Menu Button** ربات با `setChatMenuButton` روی نشانی مینی‌اپ
- ثبت دستورات `/start` و `/help`

تنها کاری که باید دستی انجام دهید (یک‌بار، در BotFather) این است که دامنه‌ی
مینی‌اپ را ثبت کنید:

```
/mybots → <ربات شما> → Bot Settings → Menu Button → آدرس https://chat.example.com
```

### polling یا webhook؟

پیش‌فرض **long polling** است (`TELEGRAM_MODE=polling`) چون به هیچ تنظیم اضافه‌ای
نیاز ندارد. اگر ترجیح می‌دهید تلگرام خودش به سرور شما بزند:

```bash
# در .env
TELEGRAM_MODE=webhook
TELEGRAM_WEBHOOK_SECRET=<رشته‌ی تصادفی — deploy.sh تولید کرده>
```

سپس `docker compose up -d --force-recreate backend`. بک‌اند خودش `setWebhook` را
روی `https://<PUBLIC_HOST>/telegram/webhook/<secret>` صدا می‌زند و هدر
`X-Telegram-Bot-Api-Secret-Token` را بررسی می‌کند.

> اگر سرور به `api.telegram.org` دسترسی مستقیم ندارد، می‌توانید
> `TELEGRAM_API_ROOT` را روی یک Bot API سرور شخصی یا پروکسی بگذارید. اگر ربات
> بالا نیاید، **سایت معمولی همچنان کار می‌کند** (خطا لاگ می‌شود و سرویس وب
> متوقف نمی‌شود).

## پورت‌ها و فایروال

`deploy.sh` دقیقاً همین‌ها را باز می‌کند:

| پورت | پروتکل | برای چه |
|---|---|---|
| 22 | tcp | SSH |
| 80 | tcp | HTTP + چالش ACME |
| 443 | tcp | HTTPS (سایت، مینی‌اپ، WebSocket، سیگنالینگ LiveKit) |
| 7881 | tcp | ICE/TCP لایوکیت (جایگزین وقتی UDP نیست) |
| **7882** | udp | ICE/UDP لایوکیت (UDP mux — تک‌پورت) |
| 3478 | udp | TURN روی UDP |
| 5349 | tcp | TURN روی TLS |
| 50000–60000 | udp | بازه‌ی relay مربوط به TURN |

> **نکته:** به‌جای بازه‌ی پورت برای ICE، از حالت تک‌پورت (`rtc.udp_port: 7882`) استفاده
> شده که روش توصیه‌شده‌ی LiveKit برای production است و برای فایروال بسیار ساده‌تر است.
> بازه‌ی 50000–60000 همچنان برای allocationهای TURN باز می‌ماند.

## به‌روزرسانی خودکار

اگر نمی‌خواهید هر بار دستی `git pull && docker compose build && up -d` بزنید:

```bash
cd /opt/anon-video
./scripts/install-autoupdate.sh          # هر ۵ دقیقه
./scripts/install-autoupdate.sh 15min    # فاصله‌ی دلخواه
./scripts/install-autoupdate.sh off      # خاموش کردن
```

یک systemd timer نصب می‌شود که هر بار:

1. `git fetch` می‌زند و اگر کامیت تازه‌ای نباشد **فوراً و بدون build** بیرون می‌آید
2. اگر بود، pull می‌کند، دامنه‌ی TURN را دوباره با `.env` هماهنگ می‌کند،
   ایمیج‌ها را می‌سازد و سرویس‌ها را بالا می‌آورد
3. سلامت را چک می‌کند

| | |
|---|---|
| وضعیت | `systemctl status anon-video-update.timer` |
| زمان بعدی | `systemctl list-timers anon-video-update.timer` |
| لاگ | `journalctl -u anon-video-update.service -f` |
| اجرای فوری | `systemctl start anon-video-update.service` |

### رفتار در حالت‌های خطا

- **build شکست بخورد** → سرویس‌های قبلی دست‌نخورده در حال اجرا می‌مانند
- **فایل‌های تحت گیت را دستی عوض کرده باشید** → به‌روزرسانی متوقف و در لاگ
  اعلام می‌شود، تا تغییراتتان بی‌سروصدا پاک نشود. تنها استثنا `livekit.yaml`
  است که `deploy.sh` خودش برای هماهنگی دامنه عوضش می‌کند و بعد از pull دوباره
  از `.env` ساخته می‌شود.
- **فایل‌های untracked** (لاگ، پشتیبان، هر چیزی که در پوشه گذاشته‌اید)
  مزاحم به‌روزرسانی نمی‌شوند
- **دو اجرای هم‌زمان** با `flock` جلوگیری می‌شود

> ⚠️ با این کار هر کامیتی که روی برنچ برود، حداکثر ظرف چند دقیقه روی سرور
> زنده می‌شود — بدون بازبینی. برای محیط واقعی یا فاصله را بیشتر بگذارید، یا
> فقط از برنچ پایدار استفاده کنید، یا خاموشش کنید و دستی به‌روز کنید.

### جایگزین: GitHub Actions

اگر می‌خواهید به‌جای هر چند دقیقه یک‌بار بررسی، **لحظه‌ی پوش** استقرار انجام
شود، workflow آماده است: [`docs/DEPLOY-GITHUB-ACTIONS.md`](docs/DEPLOY-GITHUB-ACTIONS.md)

## دستورات مدیریت

همه از داخل پوشه‌ی پروژه روی سرور:

```bash
# دیدن وضعیت
docker compose ps

# لاگ زنده‌ی همه
docker compose logs -f

# لاگ یک سرویس
docker compose logs -f backend
docker compose logs -f livekit
docker compose logs -f caddy

# ۲۰۰ خط آخر
docker compose logs --tail 200 backend

# ریستارت
docker compose restart               # همه
docker compose restart backend       # فقط یکی

# اعمال تغییرات .env یا livekit.yaml
docker compose up -d --force-recreate

# آپدیت کد (بعد از git pull)
git pull
docker compose build
docker compose up -d
docker image prune -f

# آپدیت ایمیج LiveKit
docker compose pull livekit
docker compose up -d livekit

# توقف / حذف کامل (گواهی‌ها در volume می‌مانند)
docker compose down

# حذف کامل به‌همراه گواهی‌ها
docker compose down -v

# بررسی سلامت
./scripts/verify.sh
curl -s http://127.0.0.1:3000/healthz | jq
```

سرویس‌ها با `restart: unless-stopped` تعریف شده‌اند، بنابراین بعد از ریستارت سرور
خودکار بالا می‌آیند (به شرط فعال بودن سرویس داکر: `systemctl enable docker`).

## تست

### تست خودکار مچ‌میکر

دو کلاینت WebSocket جعلی می‌سازد و کل چرخه را بررسی می‌کند:

```bash
# محلی
node scripts/test-match.mjs

# از بیرون، روی سرور واقعی
WS_URL=wss://chat.example.com/ws node scripts/test-match.mjs
```

سناریوهای پوشش‌داده‌شده:

1. نفر اول `waiting` می‌گیرد و تا نیامدن نفر دوم مچ نمی‌شود
2. با ورود نفر دوم، **هر دو** `matched` با اتاق یکسان می‌گیرند
3. توکن‌های LiveKit متفاوت، ناشناس (`anon_…`) و محدود به همان اتاق هستند
4. `leave` و قطع ناگهانی اتصال → طرف مقابل `partner_left` می‌گیرد
5. یک کاربر با خودش مچ نمی‌شود و دو بار وارد صف نمی‌شود
6. `cancel` و `ping/pong` و رد شدن `join` بدون احراز هویت
7. **هجوم هم‌زمان ۲۱ کاربر** → دقیقاً ۱۰ اتاق دو نفره و ۱ نفر در صف (تست race condition)

### تست چت داخل ربات

```bash
cd backend && npm run test:botchat
```

صف و مچ شدن، ناوردای «صف هرگز از یک نفر بیشتر نمی‌شود»، پایان و لغو،
«نفر بعدی»، نگاشت پاسخ‌ها با سقف حافظه، و جدا بودن چت‌های هم‌زمان.

### تست منطق گفتگو

```bash
cd frontend && npm run test:chat
```

پاک‌سازی متن (کاراکترهای کنترلی و جهت‌دهی دوطرفه)، بسته‌بندی روی کانال داده،
سقف حافظه و نشت نکردن شناسه‌ها، و محدودیت نرخ ارسال را بررسی می‌کند.

### تست منطق کیفیت

```bash
cd frontend && npm run test:quality
```

نردبان کیفیت، نگاشت پروفایل شبکه/دستگاه به پله‌ی شروع، و تشخیص سقف دوربین
(از جمله دوربین عمودی و نبود `getCapabilities`) را بررسی می‌کند.

### تست احراز هویت تلگرام

```bash
cd backend && npm run build && cd ..
node scripts/test-initdata.mjs
```

امضای HMAC، دست‌کاری داده، توکن اشتباه، انقضای ۲۴ ساعته و تاریخ آینده را بررسی می‌کند.

### تست TURN

```bash
node scripts/check-turn.mjs turn.example.com 3478 5349
```

### ✅ چک‌لیست تست دستی

**آماده‌سازی:** یک گوشی داخل تلگرام + یک لپ‌تاپ در مرورگر، **هر دو پشت یک VPN**.

|---|---|---|

| ۲ | روی دکمه بزن | مینی‌اپ تمام‌صفحه باز می‌شود، رنگ‌ها با تم تلگرام هماهنگ است |

| ۱۰ | در لپ‌تاپ «پایان تماس» را بزن | گوشی **خودکار** به صف برمی‌گردد: «طرف مقابل تماس را ترک کرد — در حال یافتن نفر بعدی…» |
| ۱۰.۴ | در یک دستگاه شروع به تایپ کن (بدون فرستادن) | در دستگاه دیگر «در حال نوشتن…» با سه نقطه‌ی متحرک ظاهر می‌شود و چند ثانیه بعد از توقف تایپ خودش می‌رود |
| ۱۰.۵ | دکمه‌ی 💬 را بزن و چند پیام رد و بدل کن | پیام‌ها فوری می‌رسند؛ با بسته بودن پنل، نشان قرمز تعداد خوانده‌نشده می‌آید. بعد از «پایان تماس» و شروع تماس جدید، گفتگو کاملاً خالی است |
| ۱۱ | دکمه‌ی ⏭️ «نفر بعدی» را وسط تماس بزن | تماس بسته می‌شود، طرف مقابل خبردار می‌شود و تو فوراً بدون پرسیدن دوباره‌ی اجازه‌ی دوربین به صف برمی‌گردی |
| ۱۲ | یکی را ببند (تب/اپ) | طرف دیگر ظرف چند ثانیه «طرف مقابل تماس را ترک کرد» می‌گیرد |
| ۱۳ | اجازه‌ی دوربین را رد کن | پیام فارسی «اجازه‌ی دسترسی به دوربین یا میکروفون داده نشد…» |
| ۱۴ | VPN را وسط تماس قطع کن | نشان «در حال اتصال مجدد…» و بعد یا وصل می‌شود یا پیام قطع تماس |
| ۱۵ | `https://chat.example.com/?relay=1` را باز کن | تماس باید فقط از مسیر TURN هم برقرار شود (تست TURN) |

> **بررسی «بدون نشت IP»:** در لپ‌تاپ `chrome://webrtc-internals` را باز کن. در جفت
> candidateهای انتخاب‌شده فقط آی‌پی **سرور** دیده می‌شود، نه آی‌پی طرف مقابل.

## پروتکل WebSocket

مسیر: `wss://<PUBLIC_HOST>/ws` — همه‌ی پیام‌ها JSON هستند.

**کلاینت → سرور**

| پیام | توضیح |
|---|---|
| `{"type":"auth","mode":"telegram","initData":"…"}` | احراز هویت مینی‌اپ |
| `{"type":"auth","mode":"guest","guestId":"<uuid>"}` | احراز هویت مهمان (سایت معمولی) |
| `{"type":"join"}` | ورود به صف |
| `{"type":"next"}` | پایان تماس فعلی و برگشت فوری به صف |
| `{"type":"cancel"}` | خروج از صف |
| `{"type":"leave"}` | پایان تماس |
| `{"type":"ping"}` | ضربان کلاینت |

**سرور → کلاینت**

| پیام | توضیح |
|---|---|
| `{"type":"ready","mode":…,"sessionId":…,"guestId":…}` | احراز هویت موفق |
| `{"type":"waiting","position":1,"total":1}` | در صف قرار گرفتید (جایگاه از ۱) |
| `{"type":"matched","room":…,"url":…,"token":…}` | مچ شد، به LiveKit وصل شو |
| `{"type":"partner_left"}` | طرف مقابل رفت |
| `{"type":"call_ended"}` | تماس با درخواست خودت تمام شد |
| `{"type":"cancelled","reason":"user"\|"replaced"}` | از صف خارج شدی |
| `{"type":"error","code":…,"message":"<فارسی>"}` | خطا |

**صف FIFO:** هر کس وارد می‌شود، اگر کسی در صف باشد به **قدیمی‌ترین نفرِ صف**
وصل می‌شود؛ وگرنه خودش ته صف می‌ایستد. هر کاربر فقط یک جایگاه در صف دارد —
اگر از تب یا دستگاه دیگری دوباره وارد شود، اتصال قدیمی‌تر کنار می‌رود
(`cancelled` با دلیل `replaced`) تا یک نفر چند جای صف را اشغال نکند و با
خودش مچ نشود.

> نکته: چون در این نسخه هیچ فیلتری وجود ندارد، به‌محض ورود نفر دوم بلافاصله
> جفت می‌شوند، پس طول صف عملاً همیشه ۰ یا ۱ است. ساختار صف برای وقتی است که
> بعداً فیلتر (جنسیت، زبان، منطقه) اضافه شود — آن‌وقت چند نفر هم‌زمان منتظر
> می‌مانند و `position`/`total` معنا پیدا می‌کند.

**جریان پیوسته:** دکمه‌ی «نفر بعدی» تماس را می‌بندد و بدون خاموش کردن دوربین
فوراً به صف برمی‌گردد. اگر طرف مقابل تماس را ترک کند هم خودکار همین اتفاق
می‌افتد (با امکان «لغو»). فقط «پایان تماس» است که کاربر را از چرخه خارج می‌کند.

**جلوگیری از race condition:** تمام تغییر وضعیت صف و جفت‌سازی در یک تابع کاملاً
همگام (بدون `await`) انجام می‌شود. چون Node تک‌نخی است این بخش اتمیک است و
غیرممکن است دو نفر هم‌زمان یک کاربرِ منتظر را بردارند. کارهای async (ساخت اتاق و
صدور توکن) بعد از بسته شدن آن بخش انجام می‌شوند و اگر یکی از طرفین در این فاصله
قطع شود، مچ لغو و به طرف دیگر اطلاع داده می‌شود.

## چت ناشناس داخل خودِ ربات

جدا از مینی‌اپ، یک چت ناشناس کاملاً **داخل تلگرام** هم هست. کاربر از چت با
ربات بیرون نمی‌رود.

```
کاربر ۱ : 🔎 پیدا کردن هم‌صحبت  ──▶  در صف
کاربر ۲ : 🔎 پیدا کردن هم‌صحبت  ──▶  ✅ مچ
        هر چه یکی بفرستد، برای دیگری کپی می‌شود
```

### چرا `copyMessage` و نه `forwardMessage`

`forwardMessage` بالای پیام می‌نویسد «فوروارد شده از فلانی» — یعنی ناشناسی از
بین می‌رود. `copyMessage` محتوا را **بدون هیچ اشاره‌ای به فرستنده‌ی اصلی**
کپی می‌کند و همه‌ی انواع پیام را پشتیبانی می‌کند:

متن • عکس • ویدیو • ویس • ویدیو-نوت • فایل • استیکر • گیف • مخاطب •
موقعیت مکانی • نظرسنجی • تاس • کپشن‌ها

> نکته‌ی مهم: ما **هیچ فایلی را دانلود نمی‌کنیم**. فقط شناسه‌ی پیام را به
> تلگرام می‌دهیم و خودش کپی می‌کند. یعنی محتوای عکس و ویدیو حتی از سرور ما
> **عبور هم نمی‌کند**.

### دستورها و دکمه‌ها

| | |
|---|---|
| `/chat` یا 🔎 پیدا کردن هم‌صحبت | ورود به صف |
| `/next` یا ⏭ نفر بعدی | پایان چت فعلی و جست‌وجوی دوباره |
| `/stop` یا ⛔️ پایان چت | پایان چت |
| 🗑 حذف آخرین | پاک کردن آخرین پیام خودتان از هر دو سمت |
| `/del` | حذف پیام دلخواه (روی پیام خودتان reply بزنید) |
| `/video` | باز کردن مینی‌اپ تماس تصویری |

کیبورد پایین صفحه با وضعیت کاربر عوض می‌شود (بی‌کار / در صف / در چت).

### پاسخ به پیام

اگر روی پیام طرف مقابل reply بزنید، در سمت او هم به پیام درست وصل می‌شود.
برای این کار یک نگاشت **فقط از شناسه‌ی عددی پیام‌ها** (نه محتوا) در حافظه
نگه داشته می‌شود، با سقف ۴۰۰ مدخل، که با پایان چت کامل پاک می‌شود.

### حریم خصوصی — صادقانه

| | |
|---|---|
| ذخیره روی سرور ما | ❌ نه دیتابیس، نه فایل، نه لاگِ محتوا |
| عبور فایل از سرور ما | ❌ فقط شناسه‌ی پیام رد و بدل می‌شود |
| نمایش هویت فرستنده | ❌ `copyMessage` هیچ اشاره‌ای به فرستنده ندارد |
| ماندن بعد از پایان چت | ❌ جلسه و نگاشت پیام‌ها از حافظه پاک می‌شوند |
| ماندن در تاریخچه‌ی تلگرام | ✅ **بله** 👇 |

> ⚠️ پیام‌های کپی‌شده در چتِ هر کاربر با ربات باقی می‌مانند — این ذاتی تلگرام
> است و از دست ما خارج. هر کاربر می‌تواند خودش آن‌ها را پاک کند. آنچه در
> کنترل ماست این است که **روی سرور ما هیچ‌چیز نوشته نمی‌شود**.

> ⚠️ کاربر می‌تواند خودش را لو بدهد — با فرستادن مخاطب، موقعیت مکانی یا عکسی
> که در آن چهره‌اش پیداست. هنگام مچ شدن به هر دو طرف تذکر داده می‌شود.

### ویرایش، حذف و آلبوم

**ویرایش** ✅ خودکار کار می‌کند. تلگرام آپدیت `edited_message` می‌دهد و نسخه‌ی
کپی‌شده در سمت طرف مقابل به‌روز می‌شود:

| نوع پیام | متد |
|---|---|
| متن | `editMessageText` |
| عکس، ویدیو، گیف، صوت، فایل | `editMessageMedia` — **خودِ فایل هم عوض می‌شود**، نه فقط کپشن |
| ویس، ویدیو-نوت، استیکر | `editMessageCaption` — تلگرام اجازه‌ی تعویض این‌ها را نمی‌دهد |

> چرا برای رسانه همیشه `editMessageMedia` و نه `editMessageCaption`؟ چون از
> روی آپدیت نمی‌شود فهمید کاربر فقط کپشن را عوض کرده یا خودِ فایل را.
> `editMessageMedia` هر دو حالت را پوشش می‌دهد و چون همان `file_id` استفاده
> می‌شود، فایلی دوباره آپلود نمی‌گردد.

> در حالت webhook حتماً `edited_message` باید در `allowed_updates` باشد،
> وگرنه ویرایش‌ها اصلاً به ربات نمی‌رسند.

**آلبوم** ✅ وقتی چند عکس/ویدیو را با هم می‌فرستید، تلگرام آن‌ها را به‌صورت
چند آپدیت جدا با یک `media_group_id` مشترک می‌دهد. ربات ۷۰۰ میلی‌ثانیه صبر
می‌کند تا همه برسند و بعد با `copyMessages` یکجا می‌فرستد، تا طرف مقابل یک
آلبوم ببیند نه چند پیام پراکنده.

**حذف** ⚠️ با دکمه‌ی خود تلگرام کار **نمی‌کند** و این محدودیت پلتفرم است، نه
باگ: **Bot API هیچ آپدیتی برای «کاربر پیامی را پاک کرد» ندارد.**

با آخرین نسخه‌ی منتشرشده‌ی تایپ‌های رسمی (`@grammyjs/types@5.0.0`) بررسی شد؛
فهرست کامل آپدیت‌ها این است:

```
message            edited_message      channel_post    edited_channel_post
business_connection business_message   edited_business_message
deleted_business_messages              message_reaction message_reaction_count
inline_query       chosen_inline_result callback_query shipping_query
pre_checkout_query purchased_paid_media poll           poll_answer
my_chat_member     chat_member         chat_join_request
chat_boost         removed_chat_boost  …
```

تنها مورد مرتبط `deleted_business_messages` است که **فقط** برای ربات‌های
متصل به یک حساب Telegram Business کار می‌کند، نه یک ربات عمومی. پس هیچ
رباتی با Bot API نمی‌تواند حذف را تشخیص بدهد.

**اگر جایی دیدید که کار می‌کند**، یکی از این سه است:

1. **دکمه‌ی حذف** زیر هر پیام (اینلاین یا کیبورد) — کاربر خودش می‌زند
2. **userbot** (MTProto با Telethon/TDLib روی یک حساب کاربری واقعی) — حساب
   کاربری آپدیت `updateDeleteMessages` می‌گیرد، ربات نه
3. **حساب Telegram Business** متصل به ربات

ما راه اول را پیاده کرده‌ایم:

| روش | کار |
|---|---|
| دکمه‌ی **🗑 حذف آخرین** | آخرین پیامی که فرستاده‌اید را از هر دو سمت پاک می‌کند |
| `/del` به‌صورت reply | هر پیام دلخواهِ خودتان را پاک می‌کند |

هر سه پیام پاک می‌شوند: نسخه‌ی طرف مقابل، اصلِ خودتان، و خودِ دستور.

> محدودیت تلگرام: پیام قدیمی‌تر از ۴۸ ساعت قابل حذف نیست. در این حالت پیام
> از سمت شما پاک می‌شود و اطلاع داده می‌شود که از سمت طرف مقابل نشد.

> امنیت: `/del` فقط روی پیام‌های **خودِ شما** کار می‌کند. نگاشت پیام‌ها
> جهت‌دار است، وگرنه می‌شد با reply زدن روی پیامِ رسیده، پیام طرف مقابل را از
> چت خودش پاک کرد.

### محدودیت‌های شناخته‌شده

- اگر کاربری دقیقاً متن یکی از دکمه‌ها را تایپ کند، به‌جای پیام، دکمه حساب
  می‌شود.
- ویرایش ویس، ویدیو-نوت و استیکر فقط کپشن را عوض می‌کند (محدودیت تلگرام).
- با ریستارت بک‌اند همه‌ی چت‌های در جریان از بین می‌روند (چون دیتابیسی نیست).

## گفتگوی متنی

کنار تماس تصویری، یک گفتگوی متنی هم هست — روی **کانال دادهٔ LiveKit**
(`publishData` / `DataReceived`)، نه یک سرویس جدا.

### حریم خصوصی — دقیقاً چه اتفاقی می‌افتد

| | |
|---|---|
| ذخیره در دیتابیس | ❌ اصلاً دیتابیسی وجود ندارد |
| ذخیره در فایل یا لاگ سرور | ❌ متن پیام هیچ‌جا نوشته نمی‌شود |
| ذخیره در مرورگر | ❌ نه `localStorage`، نه `IndexedDB` — فقط یک آرایه در حافظه |
| ماندن بعد از تماس | ❌ با پایان تماس، «نفر بعدی»، یا رفتن طرف مقابل، هم حافظه و هم DOM پاک می‌شوند |
| عبور از سرور | ✅ **بله** — و این را باید بدانید 👇 |

> ⚠️ **صادقانه:** چون معماری SFU است، بسته‌های گفتگو **از سرور عبور می‌کنند** و
> در همان لحظه‌ی عبور رمزگشایی می‌شوند (TLS تا سرور، TLS از سرور به طرف مقابل).
> یعنی این **رمزنگاری سرتاسری نیست**؛ فقط ذخیره نمی‌شود. برای E2E واقعی باید
> دو کلاینت کلید مشترک مبادله کنند و متن پیش از ارسال رمز شود — اگر لازم شد،
> با WebCrypto و تبادل کلید روی همان کانال داده قابل اضافه شدن است.

### رفتار

- دکمه‌ی 💬 در نوار کنترل، با نشان تعداد پیام‌های خوانده‌نشده
- پنل از پایین باز می‌شود؛ بستن پنل پیام‌ها را پاک **نمی‌کند** (فقط پنهان
  می‌شوند) — مرز حریم خصوصی، پایان تماس است نه باز و بسته کردن پنل
- کیبورد موبایل با `visualViewport` مدیریت می‌شود و روی کادر نوشتن نمی‌افتد
- نشانگر **«در حال نوشتن…»**: هنگام تایپ پیوسته هر ۲ ثانیه یک بسته‌ی خالی
  (بدون هیچ محتوایی) به‌صورت **lossy** فرستاده می‌شود؛ اگر گم شود اهمیتی
  ندارد و کانال reliable را هم شلوغ نمی‌کند. اگر ۴٫۵ ثانیه بسته‌ی تازه‌ای
  نرسد، نشانگر خودش پنهان می‌شود — پس یک بسته‌ی «تمام شد» که گم شود،
  نشانگر را برای همیشه روی صفحه نگه نمی‌دارد.

### محافظت‌ها

- پیام‌ها با `textContent` درج می‌شوند، نه `innerHTML` — هیچ HTMLی از طرف
  مقابل اجرا نمی‌شود
- کاراکترهای کنترلی و **کاراکترهای جهت‌دهی دوطرفه** (که در متن فارسی می‌شود
  با آن‌ها ظاهر پیام را جعل کرد) حذف می‌شوند
- سقف ۵۰۰ کاراکتر برای هر پیام، سقف ۲۰۰ پیام در حافظه **و در DOM**
- سقف ۱۰ پیام در هر ۵ ثانیه، بر اساس همین اتصال (نه IP)
- شناسه‌ی پیام‌ها با پیشوند فرستنده جدا می‌شود؛ وگرنه طرف مقابل می‌توانست با
  فرستادن شناسه‌ی یکی از پیام‌های شما، پیام بعدی خودتان را «تکراری» و
  حذف‌شده جلوه دهد
- بسته‌ی نامعتبر بی‌صدا دور انداخته می‌شود

## کیفیت ویدیو

کیفیت **ثابت نیست** — بر اساس سرعت اینترنت، توان دستگاه و خودِ دوربین تنظیم می‌شود.

### نردبان کیفیت

| پله | وضوح | بیت‌ریت | فریم |
|---|---|---|---|
| ۰ | 320×180 | 160k | 20 |
| ۱ | 640×360 | 450k | 20 |
| ۲ | 960×540 | 800k | 25 |
| ۳ | 1280×720 | 1700k | 30 |
| ۴ | 1920×1080 | 3000k | 30 |

### سه لایه‌ی تصمیم‌گیری

**۱. نقطه‌ی شروع (قبل از تماس)**
از `navigator.connection` (نوع شبکه، `downlink`، `saveData`)، تعداد هسته‌های
پردازنده و حجم رم یک پله‌ی شروع انتخاب می‌شود. روی Safari و iOS هیچ‌کدام از
اطلاعات شبکه وجود ندارد، پس آنجا محافظه‌کارانه از ۷۲۰p شروع می‌شود و بقیه‌اش
را حلقه‌ی تطبیق به عهده می‌گیرد.

**۲. سقف دوربین**
از `getCapabilities()` خوانده می‌شود، نه از `getSettings()` — وگرنه سقف روی
همان وضوحی که تماس با آن شروع شده قفل می‌شد. از یک وبکم ۴۸۰p هرگز ۱۰۸۰p
خواسته نمی‌شود.

**۳. حلقه‌ی تطبیق زنده (هر ۵ ثانیه)**
`getSenderStats().qualityLimitationReason` خوانده می‌شود:

| مقدار | واکنش |
|---|---|
| `bandwidth` | فوراً یک پله پایین |
| `cpu` | `prioritizePerformance()` یک‌بار + یک پله پایین + **قفل کردن سقف** روی همان پله |
| `none` | بعد از ۶ نمونه‌ی پیاپی سالم (~۳۰ ثانیه) یک پله بالا |

تفکیک `cpu` از `bandwidth` مهم است: وقتی گلوگاه پردازنده است، کم کردن بیت‌ریت
کمکی نمی‌کند و باید بار انکود کم شود.

**هیسترزیس: پایین سریع، بالا آهسته.** بدون این، کیفیت مدام بالا و پایین می‌پرد
که از کیفیت پایینِ ثابت هم آزاردهنده‌تر است.

**بدون پرش تصویر:** پایین آمدن فقط `maxBitrate` و `scaleResolutionDownBy` را
عوض می‌کند و دوربین ری‌استارت نمی‌شود. فقط وقتی بخواهیم از وضوح فعلی دوربین
*بالاتر* برویم (که `scaleResolutionDownBy` نمی‌تواند) دوربین ری‌استارت می‌شود —
حداکثر هر ۳۰ ثانیه یک‌بار.

### دکمه‌ی کیفیت

در نوار کنترل تماس، دکمه‌ای هست که حالت فعلی را نشان می‌دهد و با زدنش
می‌توان انتخاب کرد:

| گزینه | رفتار |
|---|---|
| **خودکار** (پیش‌فرض) | هر سه لایه‌ی بالا فعال |
| **بالا** | ثابت روی ۱۰۸۰p |
| **متوسط** | ثابت روی ۷۲۰p |
| **پایین** | ثابت روی ۳۶۰p — کم‌مصرف |

انتخاب کاربر در `localStorage` ذخیره می‌شود و دفعه‌ی بعد همان اعمال می‌شود.
در همان پنجره، وضوح و نرخ فریم لحظه‌ای و دلیل محدودیت هم نشان داده می‌شود
(مثلاً «اکنون: 1280×720 @ 29fps — محدود به پهنای باند»).

> در حالت‌های ثابت هم WebRTC اگر پهنای باند کم بیاید خودش پایین می‌آید؛
> این عدد یک **سقف** است نه یک تضمین.

### پارامترهای نشانی

| نشانی | نتیجه |
|---|---|
| `?q=auto` \| `low` \| `medium` \| `high` | حالت کیفیت (روی `localStorage` هم می‌نشیند) |
| `?codec=vp9` | VP9 — در همان پهنای باند بهتر، ولی روی Safari/iOS قابل اتکا نیست |
| `?relay=1` | اجبار عبور از TURN (برای تست) |

پروفایل تشخیص‌داده‌شده‌ی دستگاه در کنسول مرورگر چاپ می‌شود.

### آینه بودن تصویر

- **تصویر خودتان آینه است** (مثل نگاه کردن در آینه) — قرارداد همه‌ی اپ‌های
  تماس تصویری، چون طبیعی‌تر حس می‌شود.
- **تصویر طرف مقابل آینه نیست** — او را همان‌طور که هست می‌بینید.
- این فقط یک تبدیل CSS برای نمایش است و **روی تصویری که ارسال می‌شود اثری
  ندارد**؛ طرف مقابل همیشه تصویر واقعی شما را می‌بیند.

هر دو قانون در `styles.css` صریح نوشته شده‌اند، چون بعضی دوربین‌ها و WebViewها
خودشان جریان را آینه تحویل می‌دهند و بدون این، نتیجه روی هر دستگاه فرق می‌کرد.

> اگر **طرف مقابل** شما را آینه می‌بیند (مثلاً نوشته‌ی روی لباستان برعکس است)،
> مشکل از نمایش نیست — دوربین آن دستگاه جریان را آینه‌شده انکود می‌کند و باید
> سمت فرستنده حل شود.

### چند نکته‌ی مهم

- **simulcast در تماس دونفره خاموش است.** پهنای باند آپلود را بین چند لایه
  تقسیم می‌کند؛ این در اتاق‌های چندنفره مفید است ولی وقتی فقط یک مشترک وجود
  دارد، فقط سهم لایه‌ی اصلی را کم می‌کند.
- **VP8 پیش‌فرض است** چون روی WebView تلگرام در iOS هم کار می‌کند.
- **کیفیت با ضعیف‌ترین طرف تنظیم می‌شود.** LiveKit برآورد پهنای باند گیرنده را
  به فرستنده می‌دهد؛ اگر طرف مقابل اینترنت ضعیفی داشته باشد، تصویر شما هم
  پایین می‌آید. این ذاتی SFU است.
- **هزینه‌ی پهنای باند سرور:** در ۱۰۸۰p هر تماس حدود ۶ مگابیت در هر جهت،
  در ۷۲۰p حدود ۳٫۵ مگابیت. اگر سهمیه‌ی ترافیک محدود دارید، در
  `frontend/src/quality.ts` مقدار `IDX.high` را روی پله‌ی ۳ بیاورید.

<details>
<summary><b>گواهی HTTPS صادر نمی‌شود</b></summary>

```bash
docker compose logs caddy | grep -iE 'error|obtain|challenge'
```

- رکورد A هر دو دامنه باید به آی‌پی همین سرور اشاره کند (`./scripts/verify.sh`)
- پورت ۸۰ باید از اینترنت باز باشد (چالش ACME)
- اگر Cloudflare دارید، پروکسی (ابر نارنجی) را خاموش کنید
- Let's Encrypt سقف تعداد درخواست دارد؛ بعد از چند شکست کمی صبر کنید
</details>

<details>
<summary><b>تماس وصل می‌شود ولی تصویری نمی‌آید</b></summary>

تقریباً همیشه مشکل شبکه/فایروال است:

```bash
docker compose logs livekit | grep -iE 'ice|turn|candidate|external'
node scripts/check-turn.mjs "$TURN_HOST" 3478 5349
```

- مطمئن شوید `7882/udp`، `7881/tcp`، `3478/udp` و `5349/tcp` در ufw **و** در پنل
  ابری ارائه‌دهنده (Security Group) باز هستند
- اگر سرور پشت NAT است، در `livekit.yaml` مقدار `rtc.use_external_ip` را `false`
  کنید و `rtc.node_ip` را روی آی‌پی عمومی بگذارید، سپس
  `docker compose up -d --force-recreate livekit`
- با `?relay=1` تست کنید تا فقط مسیر TURN بررسی شود
</details>

<details>
<summary><b>ربات جواب نمی‌دهد ولی سایت کار می‌کند</b></summary>

این رفتار عمدی است — خطای تلگرام سرویس وب را متوقف نمی‌کند.

- توکن را در `.env` بررسی کنید
- اگر سرور به `api.telegram.org` دسترسی ندارد، `TELEGRAM_API_ROOT` را تنظیم کنید
- خطای `409 Conflict` یعنی جای دیگری هم همین ربات در حال polling است
</details>

<details>
<summary><b>مچ نمی‌شود / همیشه در انتظار می‌ماند</b></summary>

<summary><b>صدا پخش نمی‌شود</b></summary>

## محدودیت‌های شناخته‌شده

این نسخه عمداً ساده نگه داشته شده است:

- **بدون دیتابیس.** با ریستارت بک‌اند، صف انتظار و تماس‌های در جریان از بین می‌روند.
- **یک نمونه (single instance).** مچ‌میکر در حافظه است و برای چند نمونه باید به
  Redis منتقل شود (LiveKit خودش از قبل آماده‌ی چندنودی است).
- **قطع اتصال = پایان تماس.** طبق همین طراحی، به‌محض بسته شدن WebSocket به طرف
  مقابل `partner_left` فرستاده و اتاق بسته می‌شود. یعنی یک قطعی کوتاه اینترنت
  (مثلاً قفل شدن گوشی) تماس را تمام می‌کند. اگر خواستید تحمل‌پذیرتر شود، در
  `Matchmaker.teardown` یک مهلت چندثانیه‌ای بگذارید تا کاربر فرصت اتصال مجدد
  داشته باشد.
- **بدون گزارش تخلف / بلاک / فیلتر.** برای یک سرویس عمومی واقعی، این‌ها و همچنین
  محدودیت سنی و امکان گزارش، الزامی‌اند.
- **بدون صف چندنفره.** فقط یک جایگاه انتظار وجود دارد (دقیقاً طبق خواسته‌ی MVP).
