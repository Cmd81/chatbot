# 📹 تماس تصویری ناشناس

یک MVP برای تماس تصویری تصادفی و ناشناس که از دو مسیر در دسترس است:

1. **ربات تلگرام + Telegram Mini App**
2. **یک صفحه‌ی وب معمولی روی همان دامنه**

منطق مچ ساده است: نفر اول وارد می‌شود و منتظر می‌ماند؛ به‌محض ورود نفر دوم،
این دو به هم وصل می‌شوند و تماس تصویری شروع می‌شود. بدون فیلتر، بدون سکه و
بدون دیتابیس.

## ویژگی‌ها

| | |
|---|---|
| 🔒 **ناشناس** | نام، شماره و آی‌دی تلگرام به طرف مقابل نمی‌رسد. هویت کاربر در LiveKit یک رشته‌ی تصادفی (`anon_…`) است. |
| 🛡️ **بدون نشت IP** | کل ویدیو و صدا از SFU (LiveKit) رد می‌شود. هیچ اتصال P2P بین دو کاربر برقرار نمی‌شود و ICE candidateهای طرفین با هم مبادله نمی‌شود. |
| 🌐 **مقاوم به فیلترینگ** | TURN روی هم UDP 3478 و هم TLS 5349. کاربری که UDP ندارد از مسیر TLS وصل می‌شود. |
| 🧭 **مستقل از IP** | هیچ منطقی (احراز هویت، مچ، rate limit) به IP وابسته نیست؛ همه‌ی کاربران می‌توانند پشت یک VPN با آی‌پی یکسان باشند. |
| 📱 **موبایل‌محور** | رابط فارسی، راست‌چین، تمام‌صفحه، هماهنگ با تم تلگرام. |
| 🎥 **۷۲۰p** | پیش‌فرض ۱۲۸۰×۷۲۰ با ۳۰ فریم؛ با `?q=medium` یا `?q=low` قابل کم کردن. |
| ⚡️ **بدون دیتابیس** | مچ‌میکر کاملاً در حافظه است. |

## معماری

```
                    ┌──────────────────────────────────────────┐
   کاربر تلگرام ───▶│  Caddy  (HTTPS خودکار، ریورس‌پراکسی)      │
   کاربر مرورگر ───▶│  :80  :443                :5349 (TLS)    │
                    └────┬──────────────┬──────────────┬───────┘
                         │              │              │
             /  و  /ws   │        /rtc* │              │ TURN خام
                         ▼              ▼              ▼
                 ┌───────────────┐   ┌──────────────────────────┐
                 │   Backend     │   │   LiveKit Server (SFU)    │
                 │ Node + TS     │◀──│  :7880 سیگنالینگ          │
                 │ Fastify + ws  │API│  :7881/tcp  :7882/udp     │
                 │ grammY (بات)  │   │  :3478/udp TURN           │
                 │ مچ‌میکر حافظه‌ای│   │  :5350 TURN پشت TLS      │
                 └───────────────┘   └──────────────────────────┘
```

**چرا `network_mode: host`؟** LiveKit به پورت‌های UDP زیادی نیاز دارد و NAT داکر
برای مدیا مناسب نیست. مزیت مهم دیگر: در این حالت داکر قوانین `ufw` را دور نمی‌زند،
بنابراین فایروال واقعاً اعمال می‌شود. بک‌اند فقط روی `127.0.0.1:3000` گوش می‌دهد و
از بیرون فقط از طریق Caddy در دسترس است.

**چرا `layer4` در Caddy؟** برای اینکه TURN هم بتواند از گواهی Let's Encrypt استفاده
کند، Caddy روی پورت عمومی **5349** دست‌دادن TLS را انجام می‌دهد و ترافیک TURN خام را
به پورت داخلی **5350** در LiveKit می‌فرستد (`turn.external_tls: true`). تمدید گواهی
هم به‌صورت خودکار توسط Caddy انجام می‌شود.

## پیش‌نیازها

- یک سرور اوبونتو/دبیان با دسترسی `root` و آی‌پی عمومی
- دو رکورد **A** در DNS که هر دو به آی‌پی همان سرور اشاره کنند:

  | نام | نوع | مقدار |
  |---|---|---|
  | `chat.example.com` | A | `<آی‌پی سرور>` |
  | `turn.example.com` | A | `<آی‌پی سرور>` |

  > ⚠️ اگر از Cloudflare استفاده می‌کنید، هر دو رکورد باید **DNS only** (ابر خاکستری)
  > باشند. پروکسی Cloudflare نه TURN را پاس می‌دهد و نه صدور گواهی را.

- یک توکن ربات از [@BotFather](https://t.me/BotFather)

## نصب سریع

دو راه وجود دارد:

- **الف) دستی روی سرور** (پایین) — سریع‌ترین راه برای بار اول
- **ب) خودکار با GitHub Actions** — راهنما: [`docs/DEPLOY-GITHUB-ACTIONS.md`](docs/DEPLOY-GITHUB-ACTIONS.md)

```bash
git clone <آدرس-ریپو> anon-video
cd anon-video
./deploy.sh
```

اسکریپت به‌ترتیب این کارها را می‌کند:

1. اگر داکر نصب نباشد، نصبش می‌کند
2. فایل `.env` را می‌سازد و **کلیدهای LiveKit را تصادفی تولید می‌کند**
   (توکن ربات به‌صورت مخفی پرسیده می‌شود و فقط در `.env` با دسترسی `600` ذخیره می‌شود)
3. `ufw` را تنظیم و فعال می‌کند
4. رکوردهای DNS را بررسی می‌کند
5. ایمیج‌ها را می‌سازد و سرویس‌ها را با `restart: unless-stopped` بالا می‌آورد
6. سلامت سرویس‌ها را چک می‌کند

اجرای غیرتعاملی:

```bash
TELEGRAM_BOT_TOKEN=... \
PUBLIC_HOST=chat.example.com \
TURN_HOST=turn.example.com \
ACME_EMAIL=me@example.com \
./deploy.sh
```

بعد از اتمام، بررسی کامل:

```bash
./scripts/verify.sh
```

> 💡 **توکن ربات هرگز داخل گیت نمی‌رود.** فقط در `.env` روی سرور است و `.env` در
> `.gitignore` قرار دارد.

## تنظیم ربات تلگرام

بک‌اند هنگام بالا آمدن این کارها را **خودکار** انجام می‌دهد:

- پاسخ به `/start` با یک پیام فارسی و دکمه‌ی `web_app`
- تنظیم **Menu Button** ربات با `setChatMenuButton` روی نشانی مینی‌اپ
- ثبت دستورات `/start` و `/help`

تنها کاری که باید دستی انجام دهید (یک‌بار، در BotFather) این است که دامنه‌ی
مینی‌اپ را ثبت کنید:

```
/mybots → <ربات شما> → Bot Settings → Menu Button → آدرس https://chat.example.com
```

### polling یا webhook؟

پیش‌فرض **long polling** است (`TELEGRAM_MODE=polling`) چون به هیچ تنظیم اضافه‌ای
نیاز ندارد. اگر ترجیح می‌دهید تلگرام خودش به سرور شما بزند:

```bash
# در .env
TELEGRAM_MODE=webhook
TELEGRAM_WEBHOOK_SECRET=<رشته‌ی تصادفی — deploy.sh تولید کرده>
```

سپس `docker compose up -d --force-recreate backend`. بک‌اند خودش `setWebhook` را
روی `https://<PUBLIC_HOST>/telegram/webhook/<secret>` صدا می‌زند و هدر
`X-Telegram-Bot-Api-Secret-Token` را بررسی می‌کند.

> اگر سرور به `api.telegram.org` دسترسی مستقیم ندارد، می‌توانید
> `TELEGRAM_API_ROOT` را روی یک Bot API سرور شخصی یا پروکسی بگذارید. اگر ربات
> بالا نیاید، **سایت معمولی همچنان کار می‌کند** (خطا لاگ می‌شود و سرویس وب
> متوقف نمی‌شود).

## پورت‌ها و فایروال

`deploy.sh` دقیقاً همین‌ها را باز می‌کند:

| پورت | پروتکل | برای چه |
|---|---|---|
| 22 | tcp | SSH |
| 80 | tcp | HTTP + چالش ACME |
| 443 | tcp | HTTPS (سایت، مینی‌اپ، WebSocket، سیگنالینگ LiveKit) |
| 7881 | tcp | ICE/TCP لایوکیت (جایگزین وقتی UDP نیست) |
| **7882** | udp | ICE/UDP لایوکیت (UDP mux — تک‌پورت) |
| 3478 | udp | TURN روی UDP |
| 5349 | tcp | TURN روی TLS |
| 50000–60000 | udp | بازه‌ی relay مربوط به TURN |

> **نکته:** به‌جای بازه‌ی پورت برای ICE، از حالت تک‌پورت (`rtc.udp_port: 7882`) استفاده
> شده که روش توصیه‌شده‌ی LiveKit برای production است و برای فایروال بسیار ساده‌تر است.
> بازه‌ی 50000–60000 همچنان برای allocationهای TURN باز می‌ماند.

## دستورات مدیریت

همه از داخل پوشه‌ی پروژه روی سرور:

```bash
# دیدن وضعیت
docker compose ps

# لاگ زنده‌ی همه
docker compose logs -f

# لاگ یک سرویس
docker compose logs -f backend
docker compose logs -f livekit
docker compose logs -f caddy

# ۲۰۰ خط آخر
docker compose logs --tail 200 backend

# ریستارت
docker compose restart               # همه
docker compose restart backend       # فقط یکی

# اعمال تغییرات .env یا livekit.yaml
docker compose up -d --force-recreate

# آپدیت کد (بعد از git pull)
git pull
docker compose build
docker compose up -d
docker image prune -f

# آپدیت ایمیج LiveKit
docker compose pull livekit
docker compose up -d livekit

# توقف / حذف کامل (گواهی‌ها در volume می‌مانند)
docker compose down

# حذف کامل به‌همراه گواهی‌ها
docker compose down -v

# بررسی سلامت
./scripts/verify.sh
curl -s http://127.0.0.1:3000/healthz | jq
```

سرویس‌ها با `restart: unless-stopped` تعریف شده‌اند، بنابراین بعد از ریستارت سرور
خودکار بالا می‌آیند (به شرط فعال بودن سرویس داکر: `systemctl enable docker`).

## تست

### تست خودکار مچ‌میکر

دو کلاینت WebSocket جعلی می‌سازد و کل چرخه را بررسی می‌کند:

```bash
# محلی
node scripts/test-match.mjs

# از بیرون، روی سرور واقعی
WS_URL=wss://chat.example.com/ws node scripts/test-match.mjs
```

سناریوهای پوشش‌داده‌شده:

1. نفر اول `waiting` می‌گیرد و تا نیامدن نفر دوم مچ نمی‌شود
2. با ورود نفر دوم، **هر دو** `matched` با اتاق یکسان می‌گیرند
3. توکن‌های LiveKit متفاوت، ناشناس (`anon_…`) و محدود به همان اتاق هستند
4. `leave` و قطع ناگهانی اتصال → طرف مقابل `partner_left` می‌گیرد
5. یک کاربر با خودش مچ نمی‌شود و دو بار وارد صف نمی‌شود
6. `cancel` و `ping/pong` و رد شدن `join` بدون احراز هویت
7. **هجوم هم‌زمان ۲۱ کاربر** → دقیقاً ۱۰ اتاق دو نفره و ۱ نفر در صف (تست race condition)

### تست احراز هویت تلگرام

```bash
cd backend && npm run build && cd ..
node scripts/test-initdata.mjs
```

امضای HMAC، دست‌کاری داده، توکن اشتباه، انقضای ۲۴ ساعته و تاریخ آینده را بررسی می‌کند.

### تست TURN

```bash
node scripts/check-turn.mjs turn.example.com 3478 5349
```

### ✅ چک‌لیست تست دستی

**آماده‌سازی:** یک گوشی داخل تلگرام + یک لپ‌تاپ در مرورگر، **هر دو پشت یک VPN**.

| # | کار | انتظار |
|---|---|---|
| ۱ | در گوشی `/start` را به ربات بفرست | پیام فارسی + دکمه‌ی «📹 شروع تماس تصویری ناشناس» |
| ۲ | روی دکمه بزن | مینی‌اپ تمام‌صفحه باز می‌شود، رنگ‌ها با تم تلگرام هماهنگ است |
| ۳ | «شروع» را بزن | تلگرام اجازه‌ی دوربین/میکروفون می‌خواهد → اجازه بده |
| ۴ | منتظر بمان | «در انتظار کاربر دیگر…» + پیش‌نمایش تصویر خودت |
| ۵ | در لپ‌تاپ `https://chat.example.com` را باز کن | همان صفحه، بدون نیاز به تلگرام |
| ۶ | «شروع» را بزن | **هر دو طرف بلافاصله وارد تماس می‌شوند** |
| ۷ | تصویر و صدا | تصویر طرف مقابل تمام‌صفحه، تصویر خودت کوچک در گوشه، صدا دوطرفه |
| ۸ | دکمه‌ی میکروفون | آیکون به 🔇 تغییر می‌کند و طرف مقابل صدایت را نمی‌شنود |
| ۹ | دکمه‌ی دوربین | تصویرت قطع می‌شود و طرف مقابل تصویر تو را نمی‌بیند |
| ۱۰ | در لپ‌تاپ «پایان تماس» را بزن | گوشی پیام «طرف مقابل تماس را ترک کرد» می‌گیرد |
| ۱۱ | «تماس جدید» را بزن | دوباره وارد صف می‌شوی |
| ۱۲ | یکی را ببند (تب/اپ) | طرف دیگر ظرف چند ثانیه «طرف مقابل تماس را ترک کرد» می‌گیرد |
| ۱۳ | اجازه‌ی دوربین را رد کن | پیام فارسی «اجازه‌ی دسترسی به دوربین یا میکروفون داده نشد…» |
| ۱۴ | VPN را وسط تماس قطع کن | نشان «در حال اتصال مجدد…» و بعد یا وصل می‌شود یا پیام قطع تماس |
| ۱۵ | `https://chat.example.com/?relay=1` را باز کن | تماس باید فقط از مسیر TURN هم برقرار شود (تست TURN) |

> **بررسی «بدون نشت IP»:** در لپ‌تاپ `chrome://webrtc-internals` را باز کن. در جفت
> candidateهای انتخاب‌شده فقط آی‌پی **سرور** دیده می‌شود، نه آی‌پی طرف مقابل.

## پروتکل WebSocket

مسیر: `wss://<PUBLIC_HOST>/ws` — همه‌ی پیام‌ها JSON هستند.

**کلاینت → سرور**

| پیام | توضیح |
|---|---|
| `{"type":"auth","mode":"telegram","initData":"…"}` | احراز هویت مینی‌اپ |
| `{"type":"auth","mode":"guest","guestId":"<uuid>"}` | احراز هویت مهمان (سایت معمولی) |
| `{"type":"join"}` | ورود به صف |
| `{"type":"cancel"}` | خروج از صف |
| `{"type":"leave"}` | پایان تماس |
| `{"type":"ping"}` | ضربان کلاینت |

**سرور → کلاینت**

| پیام | توضیح |
|---|---|
| `{"type":"ready","mode":…,"sessionId":…,"guestId":…}` | احراز هویت موفق |
| `{"type":"waiting"}` | در صف قرار گرفتید |
| `{"type":"matched","room":…,"url":…,"token":…}` | مچ شد، به LiveKit وصل شو |
| `{"type":"partner_left"}` | طرف مقابل رفت |
| `{"type":"call_ended"}` | تماس با درخواست خودت تمام شد |
| `{"type":"cancelled","reason":"user"\|"replaced"}` | از صف خارج شدی |
| `{"type":"error","code":…,"message":"<فارسی>"}` | خطا |

**جلوگیری از race condition:** تمام تغییر وضعیت صف و جفت‌سازی در یک تابع کاملاً
همگام (بدون `await`) انجام می‌شود. چون Node تک‌نخی است این بخش اتمیک است و
غیرممکن است دو نفر هم‌زمان یک کاربرِ منتظر را بردارند. کارهای async (ساخت اتاق و
صدور توکن) بعد از بسته شدن آن بخش انجام می‌شوند و اگر یکی از طرفین در این فاصله
قطع شود، مچ لغو و به طرف دیگر اطلاع داده می‌شود.

## کیفیت ویدیو

پیش‌فرض **۷۲۰p (1280×720) با ۱۷۰۰ کیلوبیت بر ثانیه و ۳۰ فریم**، کدک VP8.

با پارامتر نشانی می‌توانید بدون تغییر کد آزمایش کنید:

| نشانی | نتیجه |
|---|---|
| `?q=low` | 640×360 @ 450k / 20fps — برای اینترنت ضعیف |
| `?q=medium` | 960×540 @ 800k / 25fps |
| `?q=high` | 1280×720 @ 1700k / 30fps — **پیش‌فرض** |
| `?codec=vp9` | VP9 — در همان پهنای باند کیفیت بهتر، ولی روی Safari/iOS قابل اتکا نیست |
| `?relay=1` | اجبار عبور از TURN (برای تست) |

مقدار فعلی در کنسول مرورگر چاپ می‌شود.

### چند نکته‌ی مهم

- **simulcast در تماس دونفره خاموش است.** simulcast پهنای باند آپلود را بین
  چند لایه تقسیم می‌کند؛ این در اتاق‌های چندنفره مفید است ولی وقتی فقط یک
  مشترک وجود دارد، سهم لایه‌ی اصلی را کم می‌کند. تطبیق با شبکه‌ی ضعیف
  همچنان توسط congestion control خود WebRTC انجام می‌شود.
- **VP8 پیش‌فرض است** چون روی WebView تلگرام در iOS هم کار می‌کند. VP9 و AV1
  در همان بیت‌ریت بهتر دیده می‌شوند ولی پشتیبانی‌شان روی Safari قابل اتکا نیست.
- **اگر کیفیت پایین بود ولی نشان «کیفیت شبکه ضعیف است» دیده شد**، مقصر
  پهنای باند است نه تنظیمات — با `?q=medium` یا `?q=low` امتحان کنید.
- **هزینه‌ی پهنای باند سرور:** هر تماس در حالت ۷۲۰p حدود ۳٫۵ مگابیت ورودی و
  ۳٫۵ مگابیت خروجی مصرف می‌کند (هر کاربر ~۱٫۷ مگابیت بالا و ~۱٫۷ پایین). برای
  ۱۰ تماس هم‌زمان یعنی حدود ۳۵ مگابیت بر ثانیه در هر جهت.

### تغییر پیش‌فرض

در `frontend/src/call.ts` تابع `resolveQuality` مقدار بازگشتی پیش‌فرض را
(`'high'`) تعیین می‌کند و `QUALITY_PRESETS` خود پیش‌تنظیم‌ها را.

<details>
<summary><b>گواهی HTTPS صادر نمی‌شود</b></summary>


- رکورد A هر دو دامنه باید به آی‌پی همین سرور اشاره کند (`./scripts/verify.sh`)
- پورت ۸۰ باید از اینترنت باز باشد (چالش ACME)
- اگر Cloudflare دارید، پروکسی (ابر نارنجی) را خاموش کنید
- Let's Encrypt سقف تعداد درخواست دارد؛ بعد از چند شکست کمی صبر کنید
</details>

<details>
<summary><b>تماس وصل می‌شود ولی تصویری نمی‌آید</b></summary>

تقریباً همیشه مشکل شبکه/فایروال است:

```bash
docker compose logs livekit | grep -iE 'ice|turn|candidate|external'
node scripts/check-turn.mjs "$TURN_HOST" 3478 5349
```

- مطمئن شوید `7882/udp`، `7881/tcp`، `3478/udp` و `5349/tcp` در ufw **و** در پنل
  ابری ارائه‌دهنده (Security Group) باز هستند
- اگر سرور پشت NAT است، در `livekit.yaml` مقدار `rtc.use_external_ip` را `false`
  کنید و `rtc.node_ip` را روی آی‌پی عمومی بگذارید، سپس
  `docker compose up -d --force-recreate livekit`
- با `?relay=1` تست کنید تا فقط مسیر TURN بررسی شود
</details>

<details>

## محدودیت‌های شناخته‌شده

این نسخه عمداً ساده نگه داشته شده است:

- **بدون دیتابیس.** با ریستارت بک‌اند، صف انتظار و تماس‌های در جریان از بین می‌روند.
- **یک نمونه (single instance).** مچ‌میکر در حافظه است و برای چند نمونه باید به
  Redis منتقل شود (LiveKit خودش از قبل آماده‌ی چندنودی است).
- **قطع اتصال = پایان تماس.** طبق همین طراحی، به‌محض بسته شدن WebSocket به طرف
  مقابل `partner_left` فرستاده و اتاق بسته می‌شود. یعنی یک قطعی کوتاه اینترنت
  (مثلاً قفل شدن گوشی) تماس را تمام می‌کند. اگر خواستید تحمل‌پذیرتر شود، در
  `Matchmaker.teardown` یک مهلت چندثانیه‌ای بگذارید تا کاربر فرصت اتصال مجدد
  داشته باشد.
- **بدون گزارش تخلف / بلاک / فیلتر.** برای یک سرویس عمومی واقعی، این‌ها و همچنین
  محدودیت سنی و امکان گزارش، الزامی‌اند.
- **بدون صف چندنفره.** فقط یک جایگاه انتظار وجود دارد (دقیقاً طبق خواسته‌ی MVP).
